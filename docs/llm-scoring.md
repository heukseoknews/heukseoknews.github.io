# 로컬 LLM 중요도 점수 (1단계)

`scripts/local/llm_score.py` 는 로컬 컴퓨터의 Ollama 모델로 기사 제목·매체만 보고 독자 목적(취업·연구)에 비춘 중요도를 0~5 로 매겨 `data/<채널>/llm/<YYYY-MM>.json` 에 따로 저장한다.

**1단계 범위**: 점수 파일을 만드는 도구와 데이터 형식까지다. 화면·순위·숨김은 이 점수를 쓰지 않는다. 파일은 빌드 때 다른 data 와 함께 정적 사이트에 복사되지만(공개 JSON) 화면 코드는 읽지 않는다. 기사 파일(`data/<채널>/YYYY-MM.json`)은 읽기만 한다.

## 1. 목적

현재 ★(`score_v2`)는 제목 키워드·사건 유형·출처·보도 매체 수로 정한다. 같은 키워드라도 독자에게 중요한지는 문맥에 따라 다르므로, 사람 라벨 예시를 보여 준 로컬 LLM 점수를 순서 신호로 더할 수 있는지 본다. 외부 API 를 쓰지 않고(비용·키 없음) 하루 1회 로컬에서 돌린다.

## 2. 선택한 방식과 근거

| 항목 | 값 |
|---|---|
| 모델 | `exaone3.5:7.8b`(Ollama). 한국어 제목에 맞고 8GB 메모리 Mac 에서 돈다(약 5.3GB) |
| 프롬프트 | 채널별 독자 목적 문장 + 사람 라벨 예시 8건(근거 없이 점수만), 온도 0, seed 42, 출력은 JSON `{"score": 0~5 정수}` |
| 예시 점수 | 사람 라벨 0·1·2·3 → 0·1·3·5 (`scripts/local/prompts/<채널>.json` 의 `label_map`) |
| 최종 점수 | `score_ev`: Ollama logprobs 로 점수 숫자 토큰 자리의 후보(0~5) 확률을 정규화한 기대값(0~5 연속). `score_int` 는 모델이 고른 정수(온도 0 이라 가장 확률 높은 값) |
| 버전 | `prompt_version` `v1-e2ev`(보험·AI), `v1-e2ev-noex`(금융, 임시) |

실험(사람 라벨 239건: 보험 150·AI 89 중 예시 16건을 뺀 223건, 2026-11-17, 이 Mac):

- **0~5 + 기대값이 0~3 보다 보험에서 확실히 낫다.** 사람 라벨과의 Spearman: 0~3 정수 0.56 → 0~5 정수 0.66 · 기대값 0.66~0.67(기사 단위 부트스트랩 95% 구간에서 차이 +0.10, 구간이 0 을 넘음). AI 는 0.46 → 0.47~0.49 로 **차이를 확정할 수 없다.**
- 예시 매핑은 0·1·3·5 가 0·2·4·5 보다 순서는 비슷하고, 사람이 0~1점 준 기사를 중간 이상으로 매기는 비율이 낮아(보험 41~44% 대 54%) 골랐다.
- 기대값은 같은 호출에서 추가 비용 없이 나오고, 정수의 동점을 풀어 상위 20% 정확도(보험, 관련 기사)가 81% → 90% 로 오른다.
- **근거 한 문장을 쓰게 하면** 기사당 시간이 약 4배(1.5~2.1s → 7.4~8.9s)이고 정확도는 좋아지지 않아 쓰지 않는다.
- **소수 직접 출력(0.0~5.0)** 은 값이 6~7가지뿐이고 x.5 에 몰려(보험 80%, AI 96%) 사실상 정수를 0.5 옮긴 것이라 폐기했다.
- 같은 입력 두 번: 40/40 같은 점수, 기대값 차이 최대 0.004.
- 참고(반영 안 함): 보험에서 ★와 반반 섞으면 Spearman 0.65 → 0.72(+0.06, 구간 +0.01~+0.12). 조합을 여러 개 시험해 고른 값이라 새 라벨로 다시 확인해야 한다.

실험 스크립트와 원자료는 저장소 밖에 두었다(공개하지 않음). 이 스크립트의 프롬프트는 실험 e2 와 바이트 단위로 같고, 기대값 계산도 같은 규칙이다.

## 3. 기본 실행 순서(Mac)

```bash
git pull --rebase origin main
python3 scripts/local/llm_score.py                 # 드라이런: 채널별 대상 건수·예상 시간 + 샘플 10건 실제 점수(쓰지 않음)
python3 scripts/local/llm_score.py --apply         # 승인 후: data/<채널>/llm/<YYYY-MM>.json 에 쓴다
git add data/insurance/llm data/ai/llm data/finance/llm
git commit -m "data: LLM 점수 …"                   # 코드 변경과 분리한 data 커밋
git pull --rebase origin main && git push origin HEAD:main   # CLAUDE.md 의 push 절차(실행 중 워크플로 확인 포함)
```

- 대상: `relevant` 가 false 가 아닌(숨김 아님) 기사 중 최근 3일(`--since 3`, 또는 `--since 2026-11-01`) 안에 수집됐고 이 (모델, `prompt_version`) 점수가 아직 없는 기사. `--channel insurance,ai`, `--limit N` 으로 줄일 수 있다.
- 같은 채널 기사를 묶어 연속으로 처리한다. 고정 부분(지시·목적·예시)이 system 메시지 맨 앞, 기사 제목·매체가 맨 뒤라 Ollama 가 앞부분 계산을 재사용한다(벤치마크로 확인, 8절).
- `--apply` 는 20건마다 저장한다. 중간에 끊기면(Ctrl+C 포함) 같은 명령을 다시 실행하면 이어서 한다.
- 실패 처리: logprobs 가 없거나 숫자 토큰을 못 찾으면 한 번 재시도, 그래도 없으면 `score_ev` 없이 `score_int` 만 저장(‘기대값 없음’으로 셈). JSON 형식이 틀린 응답과 통신 오류는 저장하지 않고 실패로 출력한다(다음 실행 때 다시 대상). 실패가 있으면 종료 코드 1.
- 끝나면 API(`keep_alive: 0`)로 모델을 메모리에서 내린다. 시작 전 Mac 의 메모리 압력이 높으면 경고한다(다른 운영체제는 건너뜀).
- 수집 워크플로는 `data/<채널>/YYYY-MM.json`·index.json 만 쓰고 `llm/` 폴더는 건드리지 않는다. 수집 실행 중에 llm 파일을 push 하면 그 실행의 배포에는 빠지고 다음 배포에 들어간다.
- `data/` 는 직접 편집하지 않는다는 원칙에 따라 `data/<채널>/llm/` 은 이 스크립트(`--apply`, `--merge --apply`)로만 쓴다.

### 데이터 형식 `data/<채널>/llm/<YYYY-MM>.json`

기사 id → 점수 기록 목록. 월은 그 기사가 있는 월 파일과 같다. 모델이나 프롬프트 버전이 바뀌면 같은 기사에 기록이 하나 더 붙는다(덮어쓰지 않음).

```json
{
 "6a5b5075ebcae9da": [
  {"model": "exaone3.5:7.8b", "model_digest": "c7c4…", "ollama_version": "0.30.8", "prompt_version": "v1-e2ev",
   "provisional": false, "score_ev": 3.284, "score_int": 3, "scored_at": "2026-11-18T03:10:00Z"}
 ]
}
```

| 필드 | 뜻 |
|---|---|
| `score_ev` | 0~5 기대값(소수 셋째 자리). 못 구했으면 없음 |
| `score_int` | 0~5 정수 |
| `model`·`model_digest`·`ollama_version` | 점수를 만든 모델 이름·Ollama 가 보고한 다이제스트·버전 |
| `prompt_version` | `scripts/local/prompts/<채널>.json` 의 버전. 같은 (id, model, prompt_version)은 다시 계산하지 않는다 |
| `provisional` | 라벨 예시 없는 임시 프롬프트(금융)면 true |
| `scored_at` | UTC |

파일은 UTF-8(`ensure_ascii=False`)·LF·키 정렬로, 같은 폴더의 임시 파일에 쓴 뒤 교체한다. `.gitattributes` 가 이 폴더를 LF 로 고정한다. 필드 약속은 [data-contract.md](data-contract.md) 3절.

## 4. 다른 컴퓨터(윈도우 포함)에서 점수를 만들고 Mac 에서 합치기

더 빠른 컴퓨터가 있으면 거기서 점수를 만들고 결과 파일만 옮긴다.

1. **Ollama 설치**: ollama.com 에서 운영체제용 설치 파일. 설치 뒤 `ollama pull exaone3.5:7.8b`.
2. **Python 3.10 이상과 Git** 설치(윈도우는 python.org 설치 파일·Git for Windows). 추가 패키지는 없다.
3. **저장소 받기**(공개 저장소라 로그인 필요 없음): `git clone https://github.com/heukseoknews/heukseoknews.github.io.git`
4. **벤치마크**: `python scripts/local/llm_score.py --benchmark 10`(윈도우는 `py` 도 됨). 기사당 시간과 하루 600건 예상 시간을 본다.
5. **실행**: `python scripts/local/llm_score.py --apply --since 3`. 결과는 그 컴퓨터의 `data/<채널>/llm/*.json`.
6. **옮기기**: 그 `llm` 폴더의 json 파일들을 USB·클라우드 등으로 Mac 에 복사한다(저장소 밖 임시 폴더).
7. **Mac 에서 합치기**: `git pull --rebase origin main` 뒤
   `python3 scripts/local/llm_score.py --merge <복사한 파일들>` (드라이런: 추가·기존 유지·모르는 id·잘못된 기록 건수) → 확인 후 `--apply` 를 붙여 다시 실행 → 3절처럼 data 커밋·push.
   - 기사 id 로 채널·월을 찾아 넣는다. 같은 (id, model, prompt_version)은 **기존 값을 유지**하고 새 것만 더한다. 두 번 합쳐도 바뀌지 않는다.

다른 컴퓨터에서 **직접 커밋·push** 할 때는 그 컴퓨터의 git 사용자를 GitHub noreply 이메일로 설정한다(공개 저장소에 개인 이메일이 남지 않게):
`git config user.name "Seungu Sin"` · `git config user.email "<번호>+<GitHub 아이디>@users.noreply.github.com"`(GitHub 설정 > Emails 에 나오는 값).

### 다른 컴퓨터의 Ollama 를 SSH 터널로 빌리기

저장소는 Mac 에 두고 계산만 다른 컴퓨터에서 하는 방법. 그 컴퓨터에 Ollama 와 모델이 있고 SSH 로 접속할 수 있어야 한다(윈도우는 OpenSSH 서버 기능을 켬).

```bash
ssh -N -L 11435:localhost:11434 <사용자>@<다른 컴퓨터 주소>      # 터널은 띄워 둔다
OLLAMA_HOST=127.0.0.1:11435 python3 scripts/local/llm_score.py --benchmark 10
OLLAMA_HOST=127.0.0.1:11435 python3 scripts/local/llm_score.py --apply
```

스크립트는 `OLLAMA_HOST` 한 곳과만 통신한다(기본 localhost:11434). 기록의 `model_digest`·`ollama_version` 은 그 컴퓨터 값이 된다.

## 5. 한계

- 라벨이 한 사람 것이고 239건(보험 150·AI 89)뿐이다. 예시 8건도 같은 라벨에서 골라 그 사람 기준에 맞춰졌을 수 있다.
- 금융은 라벨이 없어 목적 문장만 있는 임시 프롬프트다(`provisional: true`). 성능을 잰 적이 없다.
- 보험 라벨에 3점(꼭 봐야 함)이 1건뿐이고 그 1건이 예시에 들어가, 평가에는 3점 기사가 없다.
- 모든 LLM 방법이 후하게 채점한다(사람이 0~1점 준 기사를 중간 이상으로 매기는 비율이 보험 41~54%, ★는 28%). 그래서 **순서 신호로만 쓰고 숨김(관련도) 판단에는 쓰지 않는다.**
- 제목·매체만 본다(본문을 저장·조회하지 않는다).
- 속도는 컴퓨터마다 다르다. 이 Mac(M1, 8GB) 실험 평균은 기사당 약 2~4초였다(8절 벤치마크).

### 라이선스(결정)

EXAONE 3.5 는 연구·비상업 용도 라이선스(EXAONE AI Model License Agreement, NC)로 배포된다. 점수 파일을 만드는 1단계는 비상업 연구 용도로 본다. **실제 순위에 반영하기 전에 약관 원문을 확인한다.**

## 6. 친구 라벨이 모이면 다시 평가하기

1. 라벨(기사 id·점수만)을 `scripts/audit/labels/` 에 새 파일로 추가한다(공개 저장소라 이름·닉네임은 넣지 않음, 승인 후).
2. 그 기사들이 점수 파일에 없으면 기간을 넓혀 점수를 만든다: `--since <가장 이른 라벨 기사 날짜> --apply`(관련 기사만 대상).
3. 라벨 id 와 `data/<채널>/llm/*.json` 의 `score_ev` 를 맞춰 Spearman 을 계산한다. **프롬프트 예시로 쓴 16건(`prompts/<채널>.json` 의 `examples[].id`)은 빼고** 계산한다.
4. 판정 기준은 미리 하나만 정한다: 보험에서 "`score_ev` 와 ★ 반반"이 ★ 단독보다 Spearman 이 높고 부트스트랩 95% 구간이 0 을 넘는가. 여러 조합을 다시 고르면 우연히 좋아 보이는 조합을 고르게 된다.
5. 예시를 바꾸려면(새 라벨에서 고르기) `prompts/<채널>.json` 을 고치고 `prompt_version` 을 올린다. 옛 점수는 그대로 남고 새 버전 점수가 따로 붙는다.

## 7. 다음 단계: 자동 워커(이번에는 만들지 않음)

항상 켜진 컴퓨터가 주기적으로 점수를 매기고 push 하는 워커는 다음 단계다. 만들 때 필요한 안전장치:

- 커밋 허용 경로는 `data/*/llm/` 만(다른 파일이 바뀌면 커밋하지 않고 멈춤).
- push 전 검증: JSON 형식·필드 범위, 기사 파일 불변, 기존 기록 변경·삭제 0.
- 스위치 파일(예: 설정의 `enabled`)로 즉시 멈출 수 있게.
- 최소 push 간격(예: 하루 1~2회)과 실행 중인 수집 워크플로가 있으면 기다리기.
- 그 저장소에만, `contents: write` 만 가진 제한된 토큰(fine-grained), 만료일 설정.
- git 사용자는 noreply 이메일.

## 8. 벤치마크

`--benchmark N`(기본 10)은 기사가 가장 많은 채널의 최근 기사 N건을 같은 채널 연속으로 실제 채점하고 아무것도 저장하지 않는다. 시작 전에 모델을 내려 첫 건이 모델 로딩을 포함하게 하고, 첫 건은 따로 표시한다. 이어서 같은 기사 4건을 **두 채널 프롬프트를 번갈아** 채점하는 대조군(고정 부분이 매번 바뀌어 재사용이 끊김)과 프롬프트 처리 시간·처리 토큰 수를 비교해 앞부분 재사용이 실제로 일어나는지 보여 준다. '하루 600건 예상' = 로딩 1회 + 599 × 평균.

이 Mac(Apple M1, 8GB, Ollama 0.30.8) 2026-11-17 결과(보험 10건, 시작 때 메모리 압력 '경고' 단계):

| 항목 | 값 |
|---|---|
| 첫 건(모델 로딩 포함) | 141.3s (로딩 31s + 첫 프롬프트 처리 62s) |
| 이후 기사당 | 평균 3.25s · 중앙값 2.89s (2.2~5.4s) |
